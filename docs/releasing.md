# Releasing

pyhyi is published to PyPI together with alias packages (`pyhui`, `pyhuy`,
`pihui`, `pihuy`, `pyhuj`, `pohuj`). An alias contains no code: it depends on
the exact same pyhyi version, so installing it installs pyhyi. Aliases are
generated by `scripts/build_aliases.py`; the list lives in `ALIASES` there.

Publishing uses PyPI trusted publishing from GitHub Actions, so no API tokens
are stored anywhere.

## Versioning

pyhyi uses [Semantic Versioning 2.0.0](https://semver.org/) (`MAJOR.MINOR.PATCH`).
For release decisions, the public interface includes documented CLI commands,
flags, exit codes, configuration, machine-readable output, and Python APIs for
users and plugins.

| Bump | Use it for |
| --- | --- |
| `MAJOR` | Backward-incompatible changes to the public interface from `1.0.0` onward. |
| `MINOR` | New backward-compatible features or deprecations. During `0.x`, also use it for backward-incompatible changes and explain them in the release notes. |
| `PATCH` | Releases containing only backward-compatible fixes. |

Review all changes since the latest published release and choose the highest
applicable bump. Reset `PATCH` to zero for a minor bump. Reset both `MINOR` and
`PATCH` to zero for a major bump. A new Git hook integration or opt-in rule,
for example, would take `0.3.x` to `0.4.0`. Keep published tags and packages
immutable.

## Release a version

1. Bump `__version__` in `src/pyhyi/__init__.py` and commit.
2. Prepare patch notes covering user-visible features and fixes, plus any
   breaking changes and migration steps.
3. Make sure CI is green on `main` (the `build` job builds every package).
4. Tag and push:

   ```sh
   git tag vX.Y.Z
   git push origin vX.Y.Z
   ```

The `Release` workflow checks that the tag matches `__version__`, builds pyhyi
and the aliases, and publishes each package in its own job and environment
`pypi-<package>`. Once all PyPI jobs succeed, it creates a GitHub Release with
generated release notes for the existing tag. Add the prepared patch notes to
that GitHub Release. If a job fails, use **Re-run failed jobs** from the Actions
page.

## Trusted publisher settings

Each PyPI project needs one trusted publisher (for a project that does not exist
yet, add it as a *pending* publisher under *Account settings -> Publishing*):

| Field             | Value              |
| ----------------- | ------------------ |
| PyPI project name | package name       |
| Owner             | `marsik641`        |
| Repository name   | `pyhyi`            |
| Workflow name     | `release.yml`      |
| Environment name  | `pypi-<package>`   |

A pending publisher does not reserve the name: the project is created by the
first successful upload.

## Adding an alias

Add the name to `ALIASES`, configure its trusted publisher as above, and
release a new version: an alias always carries the same version as pyhyi.
